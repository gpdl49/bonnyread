## 3. Feasibility of D3 (and D10's metadata row)

D3 recommends a pluggable per-kind provider interface, direct calls to each source with a persistent local cache, user- or project-supplied keys, nothing hard-coded, and no hosted infrastructure in v1. **Broadly feasible — no source's terms forbid a self-hosted, non-commercial, open-source client calling it directly.** Every upstream app already does direct calls for some of these sources (Seerr → TMDb/TVDB, Sonarr → TheXEM, Eros → StashDB/TMDb, Kapowarr → ComicVine). But the following need to be reflected in D3:

**F1. TVDB wording is wrong (CORRECTED).** Users cannot "supply a key"; TVDB issues keys per project. Correct model: the project obtains one project key (free tier / OSS discount, with attribution link) and users optionally add a paid subscriber **PIN** (the model Seerr already implements, `seerr/server/api/tvdb/index.ts:113-114`). If the project key is licensed rather than user-supported, it must still be shipped in the binary — which conflicts with "nothing is hard-coded" unless "project-supplied, overridable" is allowed.

**F2. TMDb-by-default for TV is a correctness risk, not just a licensing choice.** Scene release numbering, TheXEM mappings and anime absolute numbering are keyed to TVDB ordering (Sonarr's entire DataAugmentation layer assumes TVDB ids). A TMDb-default TV provider needs an id/episode-order mapping layer (TMDb episode groups, XEM's TVDB origin) or TVDB should be the default TV provider using a project key. Scene-name mappings from `services.sonarr.tv/scenemapping` have no public replacement; D3 notes this, and it is the single hardest gap for "no hosted infra".

**F3. "Persistent local cache" must respect TMDb's 6-month cache limit (CORRECTED).** Cached TMDb data must be refreshed or expired within 6 months (§1.C). Also required: TMDb logo + disclaimer in the UI (and TVDB/TVMaze/ComicVine attribution links). Build attribution into the provider interface.

**F4. Music at 1 req/s is feasible only with aggressive caching and bulk-friendly design.** Lidarr's server exists precisely because an artist refresh fans out to many release groups/releases. Direct MusicBrainz at 1 req/s means a first import of a large library takes hours; plan for a queue with persistent cache, incremental refresh, and an **optional user-run MusicBrainz mirror** (replication feed is CC BY-NC-SA: fine for non-commercial self-hosting). AcoustID and ComicVine keys are non-commercial only — fine for the project, but note it if any commercial distribution is ever considered. Given the 2025 outage (E15), dropping `api.lidarr.audio` is strongly justified.

**F5. Books: Hardcover's terms push toward OAuth, and its quotas are tight.** Hardcover says never ask users to paste a PAT; the project should register a Hardcover OAuth client and use the **device-authorization grant** (supported), which suits a headless self-hosted server. The Free plan (5,000/day, 60/min, beta, tokens may be reset, keys expire 1 January) makes it a poor sole source for bulk library imports; OpenLibrary (1–3 req/s, dumps for bulk) as fallback is sensible. Embedding rreading-glasses is licence-compatible (GPL-3.0) but its Goodreads mode depends on unofficial access to a retired API — treat it as optional, not a default. Audnexus is being superseded by AudiobookDB; keep it behind the provider interface and track the successor.

**F6. Adult: feasible only with per-user accounts.** StashDB requires each user to register with a (publicly posted, rotating) invite code and use their own API key; new accounts are read-only, which is enough for lookups. ThePornDB needs a per-user token for full access. There is no project-level key for either, so D10's "call StashDB, ThePornDB and TMDb directly" must require user-supplied keys and degrade gracefully when absent. Eros's closed proxy also merges ids across the three sources; replicating that cross-linking (StashDB entries carry TMDb/TPDB links, per `PerformerController.cs:103,110`) is feasible but is real work, not a URL swap.

**F7. Comics: per-user key is mandatory and slow.** ComicVine's 200 requests/resource/hour and velocity detection mean large-library imports take hours (Kapowarr already batches and sleeps, `comicvine.py:426`). Metron is similar (20/min, 5,000/day). Feasible, but must be user-keyed, queued and cached.

**F8. OAuth without `auth.servarr.com` is feasible but per-provider.** Device-code flows exist for Trakt and Hardcover. For redirect-only providers (Simkl, AniList, MAL, Spotify, Goodreads OAuth1 signing) a self-hosted app with arbitrary URLs cannot use a single registered redirect; "client ids supplied by the user" (D3) is the right fallback. Note the D3 context table should list `services.sonarr.tv` (MAL relay) and `spotify.lidarr.audio` as OAuth relays too, and drop Lidarr from the `auth.servarr.com` users.

**F9. Hard-coded keys to not repeat.** Beyond those D3 names: Radarr/Eros TMDb bearer (same JWT), Seerr Rotten Tomatoes Algolia key, Lidarr Headphones key, Bazarr GA4 API secret. Telemetry (Sentry, GA4) should be absent or opt-in.

**Verdict on D3:** keep the recommendation, with fixes F1 (TVDB = project key + user PIN), F2 (TV ordering/scene mappings), F3 (TMDb 6-month cache + attribution), F5 (Hardcover via OAuth device grant, quota-aware) and F6 (adult sources require user accounts). "No hosted infrastructure in v1" is achievable; the cost is slower first imports (music, comics, books) and the loss of Sonarr's scene-mapping service, which needs bundled or community-sourced data.
